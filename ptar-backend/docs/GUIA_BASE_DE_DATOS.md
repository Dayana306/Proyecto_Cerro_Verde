# Guía para PostgreSQL — PTAR La Enlozada

Esta guía describe la configuración de PostgreSQL que utiliza el backend. El esquema aplicable está versionado en `src/main/resources/db/migration`.

## 1. Configuración esencial

- Motor: **PostgreSQL 15 o superior** (Docker usa PostgreSQL 16).
- Base: `ptar_enlozada`.
- URL local: `jdbc:postgresql://localhost:5432/ptar_enlozada`.
- Migraciones: Flyway (`V1` a `V6`).
- Hibernate: `ddl-auto=validate`; verifica la estructura sin crearla ni modificarla.

Los nombres de tablas y columnas están alineados con las entidades JPA. No renombres ni elimines campos que utiliza el backend.

## 3. Tipos y reglas de persistencia

- IDs autogenerados: columnas `INTEGER`/`BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Fechas con hora: `TIMESTAMP` (compatible con `LocalDateTime`); fechas sin hora: `DATE`.
- Cadenas extensas/GeoJSON: `TEXT`.
- Indicadores booleanos: `BOOLEAN`.
- Estados y tipos: `VARCHAR`, con los nombres exactos que utiliza el código Java.
- Importes/mediciones: `DECIMAL` con precisión y escala declaradas en el esquema.
- El sistema utiliza borrado lógico mediante estados; no añadas `ON DELETE CASCADE` sin revisar antes las reglas de negocio.

## 4. Puesta en marcha

### Con Docker Compose

Desde esta carpeta, copia `.env.example` a `.env`, personaliza las contraseñas y ejecuta:

```bash
docker compose up -d db
docker compose logs -f db
```

PostgreSQL queda disponible en `localhost:5432`. Para iniciar también la API: `docker compose up -d --build`.

### Con PostgreSQL instalado localmente

1. Crea `ptar_enlozada` y un usuario que pueda crear tablas, índices, restricciones y secuencias durante la migración.
2. Configura `DB_URL`, `DB_USER`, `DB_PASSWORD` en la ejecución de IntelliJ.
3. Si Flyway usa otra cuenta, configura `FLYWAY_USER` y `FLYWAY_PASSWORD`.
4. Ejecuta `PtarApplication`.

## 5. Migraciones Flyway

Flyway ejecuta los scripts en orden y registra el resultado en `flyway_schema_history`. No edites versiones ya aplicadas en una base compartida o con datos. Si un entorno ya aplicó migraciones en otro motor, no se puede reutilizar ese esquema/historial como si fuera PostgreSQL: se requiere una base PostgreSQL nueva y una transferencia de datos planificada. El proyecto no incluye una conversión automática de filas desde MySQL/MariaDB.

Para revisar el historial:

```sql
SELECT installed_rank, version, description, success, installed_on
FROM flyway_schema_history ORDER BY installed_rank;
```

**Respaldo:** antes de cambios en una base con datos, genera un respaldo con `pg_dump`. `docker compose down -v` elimina los datos almacenados en el volumen del contenedor.

## 6. Comprobación

Después del primer inicio, comprueba que Flyway aplicó las migraciones y que Hibernate termina la validación del esquema. Puedes ejecutar las consultas de `sql/02_consultas_utiles.sql` desde pgAdmin o DBeaver.

El modo de datos de demostración se controla con `DEMO_DATA`; no debe confundirse con los datos iniciales persistentes de `V2`.
